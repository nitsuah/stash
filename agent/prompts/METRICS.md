## Steps (per repo)

1. Confirm the local checkout at `C:\Users\<user>\code\<repo>` is on its default branch (`main` or `master`) and clean (`git status --short`). If dirty or on a non-default branch, skip and note why — never stash or discard someone else's in-progress work. In a cloud/ephemeral environment with no pre-existing checkout, clone the repo fresh instead — the dirty/non-default checks don't apply to a clone you just made.
2. Pull latest (`git pull --ff-only`) so coverage is measured against current `main`.
3. Run the repo's coverage command — Docker where available (no host toolchain required), native package-manager commands when there's no Docker daemon (e.g. a cloud agent environment):
   - Node/JS repos: prefer `docker compose run --rm unit` or `npm test -- --coverage` inside a `node:22-alpine` container, per the repo's own README/CONTRIBUTING instructions. Without Docker: detect the package manager from the lockfile present (`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, otherwise npm — e.g. `farm-3j` is pnpm), check `package.json` for a `test:coverage` script and run that one if it exists, else a `coverage` script if that exists (`<pm> install && <pm> run <whichever script is actually present>`); if neither script exists, run the test runner directly with its native coverage flag (`npx vitest run --coverage`, `npx jest --coverage`, `node --experimental-test-coverage --test tests/*.test.mjs`, etc.).
   - Python repos: prefer `pytest --cov` inside the repo's own Docker image. Without Docker: detect the dependency manifest actually present — `pyproject.toml` (e.g. `kryptos`; install via `poetry install` or `uv sync`, whichever tool the repo uses) or `requirements.txt` (`pip install -r requirements.txt`) — then run `pytest --cov` natively. Don't assume `requirements.txt` exists.
   - Java/Spring repos: `mvn test` (extract Jacoco coverage if present) — no meaningful Docker/native distinction here.
   - If no coverage script exists, log `FAILED` with the reason and move to the next repo. If the Docker build fails, retry once; if it fails again, log `FAILED` with the reason and move to the next repo — never block the whole run on one repo.
4. Extract statement / branch / function / line coverage percentages from the tool's own output. Do not estimate or infer a number from partial output.
5. Update the repo's `METRICS.md`:
   - Replace the coverage table with the measured values.
   - Update the `Last Validated` (or `Last Updated`) date to today.
   - If a metric couldn't be measured, write `TBD` with a one-line reason — never leave a stale number in place uncorrected and never invent one.
6. Commit on a branch named `metrics/<repo>-coverage-<YYYY-MM-DD>`, push, and open a **regular, non-draft PR** (`gh pr create` — never `--draft`) titled `docs(metrics): refresh <repo> coverage (<YYYY-MM-DD>)`. Never commit directly to the repo's default branch.
7. **Merge when ready — after a backoff, not immediately.** This is a single-file, machine-verified doc update — the whole point of automating it is that nobody has to remember to click merge. But merging the instant the PR opens is too early: CI hasn't finished, and a review bot (CodeRabbit or similar) hasn't had a chance to post its first pass. So:
   - **Wait 3–5 minutes after opening the PR** before checking anything. This is a real wait (sleep/poll-with-delay), not a single immediate check — its whole purpose is to let CI and commenters actually finish a cycle, not to catch them mid-run.
   - After the wait, poll `gh pr checks <PR> --repo <owner>/<repo>` (a few more short retries is fine if checks are still running) until they resolve, and read whatever review comments have posted by then.
   - If a review bot raised a real, verifiable finding (e.g. a stale number, a wrong path) — verify it against the current file, fix it, push a follow-up commit, and apply the same 3–5 minute backoff again on the new commit before re-checking. Don't merge over an unaddressed, still-open finding just because the clock ran out.
   - **All checks passed, PR is `MERGEABLE`/`CLEAN`, the diff touches only `METRICS.md`/`docs/METRICS.md`, and no review comment is still open:** re-fetch the PR's review threads one more time, immediately before merging — a bot can post its first finding in the gap between your last check and the merge command. If that re-fetch turns up a new unresolved comment, treat it like any other still-open finding (go back to the fix-and-backoff step above) rather than merging anyway. Otherwise: `gh pr merge <PR> --repo <owner>/<repo> --squash --delete-branch`. Log `MERGED`.
   - **Any check failed, is still pending after the backoff and a couple of retries, the diff touches anything beyond the metrics file, or a review comment is still unresolved:** leave it open, non-draft, for a human — log `OPEN_NEEDS_REVIEW` with the reason. Never force-merge a red, pending, or unresolved PR.
   - **If the execution environment itself refuses the merge action** — e.g. a permission/safety policy blocks autonomous merging outright, regardless of CI state (this happened in a cloud run on 2026-09-18: the environment's own classifier denied the merge step before it could even run) — that is not a failure to retry or route around. Leave the PR open, non-draft, and log `OPEN_NEEDS_REVIEW` with that reason. This step can only set the *policy* for when to merge; it cannot override a platform-level block on merging at all.
   - This is the one file in the whole agent stack allowed to merge its own PRs — every other routine (DAILY's `obn` notes, PMO, RSI) explicitly does not. That's because the diff here is fully machine-verified (a coverage number the CI run itself produced) rather than judgment-based.
8. After the push/PR/merge sequence, check the target repo's checkout back out to its default branch and pull (or do this whole step in a disposable worktree) — leaving it on the metrics branch will make step 1 skip that repo as "non-default branch" on the next run.
9. Log the result to `agent/logs/metrics-audit.log` inside wherever this run's own `stash` checkout lives — `C:\Users\<user>\code\stash\agent\logs\metrics-audit.log` on a local Windows checkout, or the equivalent path under the cloned `stash` root in a cloud/ephemeral run (not a path relative to the repo being audited — this file always lives in the `stash` checkout, regardless of which repo's coverage is being measured) as one row per repo: `| repo | result (PULLED/SKIPPED/FAILED/MERGED/OPEN_NEEDS_REVIEW) | coverage delta | note |`. Write the log locally; don't commit or push it as part of this routine — leave that for a human to batch periodically, same as `daily-repo-sync`'s logs.

## Rules

- Never fabricate a coverage number. `TBD` is always an acceptable answer; a wrong number is not.
- Never overwrite a repo's custom METRICS.md sections (health score commentary, feature-completeness tables) — only touch the coverage table and its timestamp.
- Stop after a repo's Docker build fails twice; don't retry indefinitely.
- Never open these as draft PRs. Draft status is why they used to pile up unmerged (auto-apply-plugin #62, fire #97, vhs #53 all shipped draft and were eventually closed unmerged, never landing the coverage refresh) — a draft signals "not ready," and nothing in this routine ever comes back to mark it ready.
